F1, P2
Category: Task flow and information architecture; Layout and spacing
Location: Genesis 1 reader at chapter end, 320×568 light.
Evidence: E12; K3 supplies final-verse and bottom-navigation positions.
User impact: A reader who finishes Genesis 1 has no adjacent next-chapter action in the reading flow. The persistent header offers a route through the chapter picker, but continuation requires moving attention back to navigation and choosing a chapter. The visibly empty completion area does not help the reader proceed. This affects continued reading after the scoped chapter; it does not prevent reading Genesis 1.
Proposed change: Add an explicit “Genesis 2 →” or “Next chapter: Genesis 2” link after the final verse, with enough clearance above bottom navigation. Keep the existing header chooser for nonsequential jumps.
Verification: On desktop and 390px/320px mobile, scroll to the actual final verse, confirm the whole verse and next action are reachable, activate by pointer and keyboard, and verify the destination is Genesis 2 with a clear heading and sensible focus/scroll position. Check first/last chapter boundaries separately before generalizing the pattern.
Tradeoffs: Adds a small control to an otherwise quiet reader and requires boundary handling. A text link or restrained outlined control can preserve the serif, warm reading identity.

F2, P2
Category: Content and microcopy; Task flow and information architecture
Location: Reader toolbar, especially the mobile first-visit state.
Evidence: E5, E7–E10; K3 confirms accessible names but does not establish the actions' resulting UI.
User impact: “Log” does not state what will be logged, while “Simple” does not tell a new reader whether it names the current mode or the action that will occur. Readers may hesitate before touching these secondary tools. The text-selection tip is more explicit and offers a useful local standard for wording.
Proposed change: Inspect the actual outcomes before changing labels. If the action records reading, use “Log reading.” Give the reading-mode control a name and exposed state that accurately describe its actual behavior, such as “Simple view” with a clear selected state or an action label naming the destination mode. Preserve the short visual footprint with an explanatory tooltip/accessible description where needed.
Verification: Have a first-time reader explain the expected result before activating each control; then confirm that visible wording, accessible name/state, and actual result agree. Repeat at 320px to ensure the clarified text fits without reducing targets or causing overlap.
Tradeoffs: Longer labels compete with the compact mobile toolbar. Wording should be based on actual behavior; inventing a mode distinction from these screenshots would be a mistake.
Raised by / dissent: This independent UX reviewer; no other reviewers' findings were available.
