## Configuration checks before release (no new values)

Confirm these by reading existing settings. Don't print secret values.

1. **Trusted origin.** `/native/grant` refuses any `Origin` that Better Auth doesn't trust. Production Convex
   `SITE_URL` must be `https://www.versetogether.org`, or `AUTH_TRUSTED_ORIGINS` must contain it. Website Google
   sign-in from `www` already depends on this, so it is expected to hold. The app also opens `https://www.versetogether.org/native/authorize`.
2. **`AUTH_PROXY_SECRET`** is set on both Vercel Production and Convex production. Without it, `/native/token` and
   `/native/grant` rate limits fall back to one shared bucket for everyone.
3. **Google OAuth: nothing to add.** The only OAuth redirect is still the site's own `/api/auth/callback/google`.
   The handoff to `http://127.0.0.1:<port>/callback` happens after OAuth, on the website page, and is not an OAuth
   redirect URI.
4. **Vercel Production** `NEXT_PUBLIC_CONVEX_URL` / `NEXT_PUBLIC_CONVEX_SITE_URL` point at `lovable-seal-140`, the
   deployment the app's default `DEFAULT_CONVEX` uses. The Convex JWT the app gets from `/api/auth/convex/token` is
   issued by that deployment's Better Auth (`convex/auth.config.ts`).

1. **Dev rehearsal (required).** Merge the activation PR to `dev`. The guarded Vercel build deploys
   `dev:fabulous-dogfish-606` and `https://scripture-sharing-dev.vercel.app` from the same commit
   (`docs/convex-deployment.md`). Run the release build against it with
   `VERSE_TOGETHER_SITE=https://scripture-sharing-dev.vercel.app VERSE_TOGETHER_CONVEX_URL=https://fabulous-dogfish-606.convex.cloud ./verse-together --data-dir /tmp/verse-dev-acceptance`
   and complete every acceptance step below. The keyring entry is scoped to that site, Convex deployment and profile,
   so it never mixes with production.
2. **Production.** After dev passes and the release is approved, merge `dev` → `master` the normal way.
   The guarded build runs the Next.js build, then `convex deploy`, then publishes the frontend, so the backend lands
   before the page that calls it. If the guarded pipeline is not active for Production, an authorized operator runs
   `convex deploy` for `prod:lovable-seal-140` from the same commit **before** the frontend is published.
3. Repeat the acceptance steps against production with a fresh `--data-dir`.

**Mixed versions are safe.** The old frontend works with the new backend because every change is additive. A new page
with an old backend gets a 404 from `/native/grant`, and the page shows "The desktop app couldn't be approved". An app
whose server lacks `nativeSync` gets refused calls and keeps its local copy and outbox.

## Rollback

- **Turn desktop sign-in off:** forward-fix by removing `nativeAppAuth()` from `convex/auth.ts`. Grant and token
  then return 404. Unexchanged grants expire on their own within 120 s.
- **End existing desktop sessions:** each user can revoke the "Verse Together desktop" session in Settings → Sessions.
  An operator can revoke Better Auth sessions with user agent `Verse Together desktop` (a reviewed one-off; it
  doesn't touch website sessions). The app then reports "Your session has ended" and keeps its local study.
- **Turn sync off:** removing `convex/nativeSync.ts` stops field-level verse sync, revision-checked note saves and
  deletes. The app retains unsynced changes locally. Its writes went through the same tables and validators as the
  website, so no data needs reverting. Don't restore snapshots after new writes (`docs/convex-deployment.md`).
- A Vercel frontend rollback alone leaves the endpoints live, and `/native/authorize` simply returns 404 again. That
  is safe, because nothing can be approved without the page.

## End-to-end acceptance (dev first, then production)

Use a real Google account, the release binary, a fresh `--data-dir` and the OS keyring. Record each step as
Passed, Failed, Blocked or Not run.

1. **Sign in:** Settings → Sign in → the browser opens `/native/authorize?challenge=…&state=…&port=…`. Signed out
   there: "Sign in" goes to Google, then returns to the same approval page with the same query. The page shows the
   right email. Approve → "Return to the app" → the app shows the account. The website's own session is still signed in.
2. **Decline/cancel:** Cancel on the page → the app stops waiting ("not approved"). Cancelling in the app while the
   page is open → a later Approve can't sign the app in, and the app revokes any late session.
3. **Account changed:** open the page, sign into another account in another tab, then Approve → 409 message, and nothing is approved.
4. **One use:** in the browser's network panel, confirm the callback carried a code. Replaying
   `/api/auth/native/token` with that code → 401.
5. **Sessions:** Settings → Sessions lists "Verse Together desktop". Rename the profile in the app and check that the
   website shows the new name. "Sign out other devices" in the app ends the website session and keeps the app's.
6. **Marks and notes:** mark a word range and write a verse note in the app → both appear on the website. Change only
   the highlight on the website and only the note in the app → both changes survive.
7. **Journal:** create a note in the app → it appears in the website journal. Edit it on the website, then in the app,
   with the app offline during the second edit → the app keeps both versions ("kept both"), and neither overwrites the other. Delete it in the app → it is gone on the website.
8. **Note anchors (2.13.0 behavior):** in the reader, select Alma 32:21–22 and 24 → Add to a journal note → the note
   body contains `**[Alma 32:21–22](</browse/bookofmormon/alma/32#v-21>)**` and `**[Alma 32:24](…#v-24>)**` blocks.
   After sync the website reader shows "Note" at verses 21 and 24. A note with only a reading source shows no marker.
9. **Readings, goals, guide marks, plans:** log and remove a chapter reading, change weekly goals, mark guide prose
   in the October 26 lesson, and create/edit/delete a plan. Each appears both ways.
10. **Sign out:** app sign-out ends only the app session (`get-session` with its token → null). The keyring entry
    is removed, and local study stays on this computer.
11. **Scoping:** a dev-profile token is never sent to production (different keyring entry). `--no-account` never
    touches the keyring.

## Security notes

- **`bearer()` deliberately omitted.** Better Auth 1.6.33's `bearer()` plugin has a response hook that puts the
  session token in a `set-auth-token` header, exposed to page scripts, on every response that sets the session
  cookie, including website sign-ins. That would weaken the HttpOnly cookie. The Convex plugin
  (`@convex-dev/better-auth` 0.12.5) already runs the bearer request hook, which is all the app needs.
  `tests/convex/nativeAuthHttp.test.ts` asserts that website sign-in carries no `set-auth-token` and that the
  app's bearer token works for every call the app makes. Re-run it on any Better Auth or Convex adapter upgrade,
  because the app relies on that request hook.
- The token exchange and bearer calls are sent as the app sends them, with no `Origin` and no cookie, and they pass on the
  real Better Auth handler. Only `/native/grant`, which runs on a cookie session, requires the trusted origin.
- Codes are stored only as SHA-256 hashes, are single use (consumed before verification), and are bound to an
  S256 challenge. The callback goes only to the `127.0.0.1` IP literal.
