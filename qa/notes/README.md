# Notes component QA

Run `npm run qa:notes` and open `http://127.0.0.1:4189/qa/notes/index.html`.

This separate Vite harness renders the actual `JournalWorkspace`, `JournalNoteEditor`, Markdown editor and reading-log dialog with explicitly synthetic fixtures. Its auth, mutation and routing shims never contact Clerk, Convex or a production API. It is outside Next's app routes and is not a product sample mode. Fixture state resets on page reload. The fixtures give October 21 five notes (one published, so read-only; one with a long title, a 220-character excerpt and a long source label; one with an unbroken title and excerpt) and a reading, October 20 an older verse note and October 18 one note. October 21's first note starts as the active note, as if arriving from the reader's sidebar with it active, but like `/notes` the harness still opens on the calendar for October 21 (a phone shows only the month; desktop shows the month and that day's chooser) until a note is chosen; add `?active=none` to arrive without an active note. Day, open and close state go through the same `journalView.ts` model as the app, with the active note standing in for the provider's, and opening, closing, Back and Forward go through the same `useJournalHistory` hook as `/notes` (a reload keeps the open note's history entry but resets the fixtures). The harness header/navigation is only scaffolding; the real app retains its existing header and bottom-nav components.

Backend ownership, persistence, revision conflicts, legacy retention and idempotency are covered separately by `npm run test:notes` using Convex's in-memory test helper. This harness does not establish authenticated end-to-end backend verification.

Add `?sidebar` to render the actual desktop `NotesSidebar` beside a synthetic reader, using the same note fixtures and save outbox. This covers the dated note chooser, long cards and sources, switching, Markdown editing, published read-only notes, new source-linked notes and collapse/reopen. Use `?sidebar&active=none&empty=true` for the empty state, or `?sidebar&createError` for a creation failure. The sidebar stays desktop-only, as in the app; mobile reader actions continue to open `/notes` through `NotebookPanel`.

Add `?panel` to render a chapter page's combined Log and Notes panel: the actual `NotesSidebar` with its Log view (desktop) or `NotesSheet` (below 1024px), opened by a synthetic stand-in for the reader header's Log button. The Log view is the actual `ChapterLogView` (mark-read toggle and the embedded `ReadingLogForm` with verse and day fields); "Go to 1 Nephi 3" switches the synthetic chapter while the panel stays open, and the synthetic reading history lists what was logged. Request ids are deduplicated like the server's; `?panel&logFail` or `?panel&markFail` makes the first save land but report an error, so a retry (also after collapsing and reopening the panel) must not add a second history row.

Note deletion: every non-published note's editor (calendar, `?sidebar` and `?panel`, including the phone sheet) has a **Delete note** button that asks for confirmation before deleting; published notes have none. The harness stands in for the provider's `deleteDraft` with the same outbox coordination (`JournalOutbox.remove`), a 400 ms synthetic delay, and a synthetic refusal of published notes. A deleted note leaves the fixtures and stops being active; in the calendar it closes through the same history step as the note's X if it is still in view, while a calendar, day or other note chosen before the deletion finishes stays as it is. Add `?deleteError` to make every deletion fail, or `?deleteError=once` to fail only the first attempt so a retry succeeds. Fixture deletions reset on reload. The Convex `deleteDraft` mutation's ownership, cleanup and published refusal are covered by `tests/noteDeletion.test.ts`, and the outbox's save/delete races by `tests/journalOutbox.test.ts`; neither this harness nor those tests exercise an authenticated deployment.

The build reports that `CONVEX_SITE_URL` is unset; this build does not verify authenticated runtime configuration. Without a public Convex URL the initial build failed during prerender because the app lacks a Convex auth provider.
- **Passed** — collaborative-browser fixture checks at 1280×800 and 390×844: confirmation focuses Cancel, cancellation preserves the note and restores focus, successful deletion removes the note and its history entry, sidebar failure retains text and retry succeeds, published notes have no delete action, and phone-sheet Escape dismisses only confirmation. Successful sheet deletion returns to the list while keeping the sheet open. Light and dark confirmation layouts have no horizontal overflow; dark confirmation uses text `rgb(24, 23, 21)` on `rgb(227, 144, 122)`.
- **Passed** — delayed deletion regression in the phone journal: the synthetic 400 ms response was delayed to 15 seconds; after confirming deletion, closing the note and returning to Calendar, the completed deletion updates the day from five notes to four while Calendar stays visible. The original implementation changed Calendar back to the day chooser; the repaired view action and history no-op prevent this.
- **Failed** — whole-repository ESLint reports 142 errors and 20 warnings in unchanged files. Changed files pass targeted lint.
- **Not run** — authenticated browser-to-deployed-Convex deletion, deployment, push or PR creation. Fixture writes remain in memory and reset on reload. Backend functions and schema are unchanged.

The existing history settling window still applies: an action taken before the browser finishes stepping back off a note entry can be superseded by another action during that same traversal (normally a frame, with a one-second fallback). The completed-navigation regression above is covered.
